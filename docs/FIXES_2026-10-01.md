# BDBE Fixes — Grand Theft Bayou East

Everything fixed in this session, written up so it survives a context reset.
Each entry is: what was wrong, why it was wrong, what changed, and how it's
proven. Bugs verified by reintroducing the defect and watching the test fail are
marked **[proven]** — a test that has never been seen to fail proves nothing.

Repo: `grand-theft-bayou-2` · Branch: `main` · Tests: 48 in `npm test`, all green.

---

## 1. The game wouldn't load — `ReferenceError: M is not defined`

**Severity: critical.** Every player saw *"The game couldn't finish loading"* on
the deployed build.

```
ReferenceError: M is not defined
    at buildLevel (src/main.js:3526:15)
    at async boot (src/main.js:6520:3)
```

**Cause.** Commit `ee50579` ("Paint the lanes onto US-167") added
`markUS167()` and hoisted `const M = createMarkings(...)` out of `buildLevel()`
into it. But `buildLevel()` also passed `markings: M` down to
`createOrleaRouge()`, and that line kept pointing at a name that no longer
existed in its scope. `buildLevel()` threw before the first district finished.

**Fix.** `buildLevel()` now creates its own markings instance:

```js
const cityMarkings = createMarkings({ y: 0.031 });
...
orlea = createOrleaRouge({ ..., markings: cityMarkings, ... });
```

A separate instance is correct rather than a workaround: US-167's paint sits at
the highway's height, OrleaRouge's streets at `y 0.03`, and it flushes its own
meshes. One markings object cannot be at two heights.

**Why the test suite missed it.** `node --check` only parses, so it stayed happy.
And every QA harness calls the district modules *directly* — `createOrleaRouge`,
`createMetro`, and so on — so `buildLevel()` itself was never executed by any
test. Green tests and a broken game were not contradictory; nothing ran the load
path.

### The test that now covers it — `tools/qa/main_js_scope_test.mjs` **[proven]**

`main.js` has no unbound identifier in the load path. Building this was harder
than the bug, and the reason is worth recording: a lexical sweep with no JS
parser available (no acorn, no eslint in the repo) fails in four separate ways,
and **every one of them failed silently by passing against the real bug.**

1. **Three sequential strip passes don't work.** A `//` comment whose prose
   contains a capital (`// the GAS·N·GEAUX station`) gets eaten by the
   regex-literal pass, whose body runs on until it finds a `/` on some later
   line. Strip line comments first instead, and a genuine regex literal
   (`/Taco|Grill/`) is eaten as a comment. **Fix:** one left-to-right character
   scan that decides comment vs string vs regex per position.

2. **Division looks like a regex.** `-Math.PI / 2],  // Chatboro` — the `/` after
   a digit is division, but the sweep read `2],    // Chatboro, by the spawn` as
   a regex body and leaked the comment's words. **Fix:** a `/` only opens a
   literal when the last significant character can't end a value.

3. **File-wide binding is not scope.** `bound.has("M")` was *true* — `M` is
   declared in `markUS167()`. The question was never "does this name exist" but
   "does it exist **here**". **Fix:** slice out `buildLevel`'s own body and
   require the binding inside that slice.

4. **The check read the wrong text.** The explanatory comment *added alongside
   the fix* contains the literal string `const M`, and the scope check was
   matching against the raw file, finding it there and concluding `buildLevel`
   was fine. **Fix:** match against the comment-stripped source. Comments are not
   bindings.

There is a fifth, and it is the one that would have shipped a green test that
catches nothing:

5. **An arrow-param rule that also matched call sites.** `/\(([^)]*)\)\s*=>/`
   matches `createOrleaRouge({ scene, ..., markings: M })` — a *call*, not a
   parameter list — and then parses `markings: M` out of it and binds `M` as a
   destructured parameter. That is the exact bug, quietly marked as fixed.
   **Fix:** require a destructuring brace to open the list, so only real
   parameter lists match.

**Verification:** reintroducing `markings: M` makes the test exit 1 with
`FAIL the markings: M handed to OrleaRouge is bound inside buildLevel itself`.
Restoring the fix returns exit 0.

## 2. Bystanders fled forever

**Cause.** `npc.js`'s panic branch set an 8–12 s flee countdown but never latched
`e.panic`. The next `think()` re-entered the branch and reset `stateT` every
frame, so a bystander in earshot of gunfire ran and never stopped.

**Measured:** a pinned bystander in earshot of sustained gunfire recorded **187
flee-resets in 60 s, with `stateT` never dropping below 8.0 s**. With the latch,
**7 resets** — one per completed flee cycle, which is correct: it runs, calms,
and the next burst frightens it again.

**Test:** `tools/qa/npc_panic_test.mjs` **[proven]**. An earlier version of this
test **passed against the bug**, for the same class of reason as #1: the stub's
`resolveCollision` returned `{x: 0, z: 0}`, which *teleported* the ped 103 m away
instead of pinning it, so the panic branch was never re-entered. A test that
cannot reach the code under test is not a test.

## 3. Pip-Boy had two real Fallout skins

**Was:** a cyan-to-magenta gradient panel with an RGB scanline wash. That is
synthwave, not a Pip-Boy.

**Now:** two Fallout themes as *data*, not two stylesheets —
`fo3` (amber phosphor, the 2008 look, **default**) and `vegas` (green, the 2009
one). Both live in a `THEMES` table painting `--pip-*` custom properties on
`<html>`, so the two skins share every class name and switching is a single
attribute flip. The CRT scanline and phosphor bloom are preserved.

The choice persists in `localStorage`; a toggle sits in both the
character-creation and in-game headers. `applyPipboyTheme()` now returns the skin
it *actually painted* rather than the one it was handed, so a corrupt saved value
falls back to FO3 instead of throwing on a screen with no label.

**Tests:** `tools/qa/pipboy_theme_test.mjs` (13 checks) — both skins define every
colour, are genuinely different, FO3 is amber, Vegas is green, the choice
survives a re-read, and a nonsense value falls back safely.

**Harness fix it required:** `tools/qa/lib/browser_stub.mjs` gained a real CSS
property store on `documentElement`. The old stub's `getPropertyValue` returned
`""` for everything, so **no test could tell amber from green** — the Pip-Boy
could have painted one colour for both skins and the suite would have passed.

## 4. Both launch gates removed

**Access password — deleted outright.** It was a client-side hash check with the
hash sitting in the source beside the hash it checked. It was never access
control; it just stopped a casual visitor landing on the build by guessing the
URL. Nothing else referenced it.

**18+ popup — dialog gone, checks intact.** The popup's only job was setting
`window.__GTB_AGE_GATE_ACKNOWLEDGED`, which is now set at load:

```html
<script>window.__GTB_AGE_GATE_ACKNOWLEDGED = true;</script>
```

This was a deliberate choice over simply deleting the dialog. `adultContent.js`
adopts the static buttons and reads that flag; `characters.js` refuses to return
an actor who is not past the age floor; `act.js` refuses to cast one. Removing
the dialog *without* the flag would have left a truthy non-markings object and
removed a visible warning while leaving no actual check. **Nothing underage can
be cast** — the player simply isn't asked at every launch. `adult_gate_race_test`,
`act_test` and `adult_content_test` all still pass.

## 5. Speech box restyled to the town, not the menu

**Was:** hot pink (`#ff4fb3`) on near-black. That palette belongs to the title
screen and read as a different product the moment you were actually in the game.

**Now:** a signboard in the world's own palette, sampled from `townkit.js`'s
`PALETTES` — aged brass, weathered brown, cream trim. Stage directions read
cooler and quieter than the voice so the eye can skip them.

Every text/background pair was measured against **WCAG AA**; two marginal greys
(3.9:1 and 4.0:1) were lifted to 5.8:1 and 5.5:1 rather than shipped.

## 6. Skill creation now in every mode

**Was:** the Pip-Boy was Zombie-only. Story and Free Roam started with whatever
SPECIAL the character happened to carry, so the skill system was unreachable
outside Zombie mode.

**Now:** `confirmCharacter()` is async and asks for a build in all three modes,
**before** `beginGame()` and before any campaign's opening cutscene. That order
is asserted, because applying a build after `prologue.start()` lands it on a
cutscene that is already playing.

**Two holes found while wiring it up:**

- The select screen's Enter key re-entered `confirmCharacter()` while the player
  was still choosing, opening a **second Pip-Boy over the first** and launching
  the game behind it. → re-entry guard.
- `launchFromSave()` was sync and would have popped the Pip-Boy over a loaded
  game and **re-rolled a character the save already owned**. → `restoringSave`
  flag, cleared once `applySave()` has the character.

Cancelling returns to the character select; a thrown build warns and falls through
rather than throwing into the launch.

**Test:** `tools/qa/launch_build_test.mjs` (15 checks) — including explicit
*ordering* assertions (pip < begin, pip < prologue, pip < alternate, pip < greedo).

## 7. Main menu is the mode list, and it goes fullscreen

**Was:** `Start Game` → a second panel offering Story / Free Roam / Zombie
Survival Nightmare / Multiplayer. An extra click before the game, and it
presented the two free-roam modes as though they were two different games.

**Now the root menu is the list:**

- **Free Roam** — starts the game
- **Story — New**
- **Load Game**
- **Multiplayer**
- **Options** — the existing panel
- **Exit Game** — the existing quit confirm

**Zombie Survival Nightmare removed as a menu entry.** It is a free-roam
variant (hard, no respawn, endless spawner), not a second game, and you asked
for one free roam rather than two. Its code is untouched and still runs from a
**loaded save** — `launchFromSave()` dispatches on `d.mode` — so old zombie saves
still work; there's just no way to start a new one. Removing the `zombieBtn`
declarations also removed a null dereference that would have fired during boot
once the element left the DOM.

**Multiplayer kept.** It's your real work, not a duplicate mode, so I didn't
delete it without asking.

**Fullscreen** is requested as the menu appears — on the first real interaction,
not at paint time. Browsers only grant `requestFullscreen()` from inside a user
gesture, so a call while the menu paints is *silently refused* and would have
looked like a broken feature. Bound to `pointerdown`/`keydown`/`click` with
`{ once: true }`, guarded by a flag, skipped if already fullscreen, and the
returned promise's rejection is caught — it rejects when the document isn't
visible, so without that catch every load logs an unhandled rejection.

## The pattern worth remembering

Four of the six bugs here were invisible to a green suite. The reasons were
always one of two things:

1. **Nothing ran the code.** `buildLevel()` was never executed by any test; the
   harnesses call district modules directly. A test that cannot reach the
   defective path is decoration.
2. **The test was wrong in a way that passed.** A stub that teleported the ped
   out of earshot. A `getPropertyValue` that returned `""`. An arrow-param regex
   that matched a call site and "bound" the very name under investigation.

The only defence is to **reintroduce the bug and watch the test fail.** Every
test above marked **[proven]** was checked that way. The ones not marked that way
have not been, and I'd treat them as unproven until they are.
